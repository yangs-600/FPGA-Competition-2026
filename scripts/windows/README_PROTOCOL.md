# 九例 Windows 验收协议

本脚本读取包内 `manifest.json` 和显式的 `cases_current.json`，只接受九个用例。清单中的每项需要 `name`、`top`、相对包目录的 `path` 和原始文件的 `sha256`。`id` 可以代替 `name`。所有用例使用同一候选程序和同一已固定的 ABC 资源，脚本不提供逐用例选择 ABC 脚本的接口。

最终交付包附带完整、隔离的 Python 运行时。解压后双击 `run_cases.cmd`，或在 Windows PowerShell 中运行：

```powershell
.\run_cases.cmd
```

启动器用 `%~dp0` 动态定位包目录，调用包内 `runtime\python.exe`，不需要预先安装 Python。也可从其他目录直接调用 Python 脚本并用 `--package` 指定解压位置。程序、资源、输入、临时目录和报告位置均在运行时从该目录计算，不依赖构建机器的绝对路径。当前 Yosys/ABC 构建仍要求英文解压路径。

## 测量顺序

1. 校验两版程序、ABC、资源、用例指纹。两版 ABC 二进制必须一致。
2. 每个用例先运行原版十次预热。正式测量之前不运行候选版，也不提前导出候选版形式网表。
3. 首轮顺序固定为原版、候选版。每一次完整综合同时记录墙钟耗时、包含 ABC 子进程的 CPU 时间，以及 Yosys 主进程峰值工作集。
4. 如果首轮原版耗时不足一秒，且候选的墙钟时间或峰值工作集相对增加超过 5%，追加五轮原版、候选版配对复核。正式结果采用追加五轮中各版本的算术平均值之比；首轮完整保留、单独展示，不混入五轮平均。
5. 首轮原版超过十秒时只测一轮。原版一至十秒时也只测一轮，并在报告注明官方未详细规定此区间的复核规则。
6. 性能测量结束后才额外运行网表导出流程，导出 ABC9 后、最终 Cyclone IV LUT 映射前的原生 RTLIL。导出运行不计入性能数据。

上述“五次复核不含首轮”和“以原版运行时间区分大小用例”是对表格 `Sheet1!C132` 的明确实施解释，原问答没有规定这些细节。报告保留全部原始记录，以便官方按其他解释复核。脚本不会修改杀毒软件或任何安全设置。

墙钟时间是本次主判定指标，符合新版推荐的 `Measure-Command` 类型；CPU 时间保留为辅助证据。最终配套 `windows_metrics.measure` 从 `CreateProcessW` 调用之前开始计时，到主进程退出为止，包含程序创建、Job Object 绑定和主线程启动。两版使用完全相同的计量代码，在同次完整综合中测得时间和主进程峰值工作集。

## 判定和边界

逻辑资源按最终网表的 LUT 加独立 NOT 计数。九例逐例不能增加，并对九例的相对减少率取算术平均，要求至少 20%。DFF 变化另行列出，不据最新 `C130` 的“不关注 DFF 增加”表述作额外硬性否决。

每例墙钟时间和峰值工作集均不超过原版 1.05 倍时标为效率满分范围；任一超过 1.15 倍时标为效率零分范围。中间区间只标记需审阅，不臆造评分公式。绝对 60 秒与 2 GB 按所有正式与复核候选样本的最大值核对，不取最好结果。

`report.json` 和 `latest-current.json` 最多报告 `MEASUREMENTS_PASS_FORMAL_PENDING`。导出 RTLIL 不等于证明通过，必须另外完成 EQY；失败时记录 `FAIL` 和原因。历史四例 v14 证明不能替代新九例及新二进制的证明。
