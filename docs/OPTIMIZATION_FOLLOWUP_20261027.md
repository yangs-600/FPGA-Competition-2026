九例统一使用原固定脚本，未按用例切换：


未修改原版、ABC 源码、其他优化 pass 或计量协议。Windows 使用同一原版 PE、ABC 和 DLL；v22 基于保留的匹配对象增量编译，不能称为清洁重建。

## 一次独立阶段诊断

在全新、存在即拒绝覆盖的目录中复制同 SHA 程序，固定执行原版十次预热，再原版→候选第一次→候选第二次三个带 `-t` 的完整 test1 流程。未运行第二次正式九例协议。父进程在 `Popen` 前取外部 QPC，PIPE 逐行记录到达时间与 Yosys 内部时间戳，保留全部日志和命令。

| 诊断量 | 候选第一次 | 候选第二次 |
|---|---:|---:|
| 外部完整耗时 | 1.4190669 秒 | 0.3564581 秒 |
| `Popen` 调用耗时 | 0.4623101 秒 | 0.0071891 秒 |
| 首条日志到达父进程 | 0.7580081 秒 | 0.0423607 秒 |
| PMUX 入口至结束日志 | 0.001637 秒 | 0.001804 秒 |
| ABC command 至随后 AIGER frontend 入口 | 0.393526 秒 | 0.127974 秒 |

新复制原版的第一次预热也慢：外部 1.4525393 秒，其中 `Popen` 0.4175528 秒。诊断复现了首轮额外开销，但幅度与正式测量不同。PMUX 日志区间没有变慢；较大差异出现在进程创建调用、首条可见日志之前及 ABC 调用区间，不能将数百毫秒全归因于 PMUX。

解释边界：`Popen` 与首条到达间隔互相包含，不能相加。PIPE、日志缓冲、父进程调度和新复制路径都与正式计量不同；首条到达只能给出含缓冲的上界。Yosys `-t` 的时间原点惰性初始化，不覆盖之前的加载/初始化；ABC 区间包含启动、运行、等待、日志过滤及到下一条 Yosys header 的工作。它不是 ABC 纯 CPU。Windows 的 `PerformanceTimer::query()` 在该源码中返回零，因此没有用 `-d` 或 `--perffile` 作阶段计时。**尚未确定具体的加载、缓存、文件系统、调度或安全软件原因，未声称这些原因已消除，也未改变安全设置。**
